bump: minor

A signing manifest can take its digests from a reviewed build inventory instead of having them written into `release.yaml` for every release. With `pins: inventory` in the `signing` section the manifest keeps the reviewed structure only, and the digests come from a `zeo.build-inventory/v1` file that goes through an ordinary pull request (`release/inventory/<version>.json`). The inventory names its release `version`, and its path is always `release/inventory/<version>.json`. The signing service admits it only when the commit is merged to the default branch, holds exactly those bytes at that path, the pull request that produced the commit added or changed that very file, and the latest `council/approve` status on the commit was created by the adopted approver (otherwise `inventory_unreviewed`, or `review_unreadable` when GitHub cannot be read). `zeocore release sign`, `verify`, `receive` and `pack` take an optional `inventory` (and `pack` an `inventory_path` and `version`); a request without them is unchanged byte for byte. A refusing port, `zeo_core.release.signing.event_auth`, is added for authenticating the release event after the seal: it checks that the seal verified and that the event is the unchanged canonical document, and then always holds, because no mechanism for a JSON payload is adopted. Files read from GitHub are bounded, and a repeated key in an inventory or an event is refused. Manifests that pin their own digests are not affected.
